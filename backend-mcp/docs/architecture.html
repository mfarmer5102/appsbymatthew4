backend-mcp

Portfolio MCP Server

A standalone Node service that hands an MCP client four read-only tools over the portfolio's Postgres star schema. It speaks MCP's Streamable HTTP transport, deployed behind AWS Lambda; the identical handler runs locally behind a plain Node HTTP server for development.

What happens when a model calls a tool

Every call lands on the same five-stage path once it reaches McpServer, whether it arrived at a real Lambda invocation or at _local.mjs's dev server — both call the same handle_lambda_request. The only real branch is the semantic tool, which buys a vector from OpenAI before it can query.

How the objects get built

One composition root wires everything, whichever entry point calls it. No class below it imports a singleton, so a test constructs its own Container and gets its own pool.

Constraints worth knowing

Local dev calls the same handler

_local.mjs and scripts/inspect.js just invoke handle_lambda_request behind a plain Node http server — no second, divergent code path for local development to drift from what Lambda actually runs.

Read-only by design

Unlike the sibling pool in backend/, there is no transaction helper here. Three connections, a 15s statement timeout, and nothing that writes.

Queries qualify the schema

The schema name travels on the connection object, so repositories write apps_by_matthew.dim_… rather than leaning on search_path.

The CA ships with the code

Supabase's pooler is rooted in a CA that Node does not trust. The bundled cert under certs/ must stay in any deploy package.

Named statements are off

The transaction-mode pooler does not support them, so no query passes a name.

Model version is a filter

Embedding reads filter on model_version. Without it, a second model's vectors would duplicate every row.

Stateless per call

Lambda gives no guarantee two requests land on the same instance, so _aws_lambda.mjs builds a fresh McpServer and opens the Streamable HTTP transport in stateless mode on every invocation. Only the Postgres pool and OpenAI client persist, as Container singletons across a warm start.

Secrets differ by runtime

Locally, Environment loads .env. In Lambda, SecretConfig resolves both secrets from Secrets Manager's prd-secrets at module scope, before Container is built.
